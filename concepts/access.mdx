## Overview

Studiograph is multi-user out of the box. Authentication runs locally inside the workspace, backed by SQLite — there's no external identity provider. Access control happens at two layers:

- **Workspace role** — `owner` or `member`. Controls user management, billing, and workspace-level settings.
- **Folder role** — `admin` or `editor`, granted per folder via the `folder_access` table. Controls who can read, write, and manage each folder.

Workspace ownership does **not** automatically grant folder admin on folders the owner isn't a member of.

## Authentication modes

A running server is in one of three modes:

- **Open mode** — no users configured. All requests pass through with full access. Useful for local dev.
- **Authenticated mode** — at least one user exists. Endpoints require a JWT cookie or a Bearer token.
- **First-run setup** — `userCount === 0` and the server has been hit. The web UI shows `/setup` to create the first owner.

When the first owner is created, they're auto-granted folder-admin on every existing non-personal folder so the workspace doesn't render empty.

## Credentials

Studiograph accepts three credential forms on the same endpoints:

| Credential | Where it goes | Notes |
|---|---|---|
| Session JWT | `__sg_token` httpOnly cookie | Set by `POST /api/auth/login`. 7-day expiry. |
| Workspace API key | `Authorization: Bearer <key>` | One per workspace. Synced via `auth-seed.json`. Regenerate via `POST /api/auth/api-key/regenerate`. |
| Per-user API token | `Authorization: Bearer sg_<token>` | Minted in **Settings → Connectors → Studiograph MCP**. Carries the owning user's identity; access is filtered per request. |
| HTTP Basic | `email:password` | Used by the embedded Git HTTP server and `studiograph join`. |

Per-user `sg_` tokens are sha256-hashed at rest. The raw token is shown once at mint time and never again.

Login endpoints (web + Git HTTP Basic) are rate-limited per email — 5 failed attempts trigger a 15-minute lockout.

## Workspace roles

| Action | Owner | Member |
|---|:---:|:---:|
| Create / delete users | yes | no |
| Reset another user's password | yes | no |
| Transfer ownership | yes | no |
| Export auth seed | yes | no |
| Regenerate workspace API key | yes | no |
| Mint per-user API tokens | yes (own) | yes (own) |

The owner cannot delete themselves. Ownership transfers via `POST /api/auth/transfer-ownership` and requires the target to be an existing user.

## Folder roles

Folder roles are granted per `(user, folder)` pair in the `folder_access` table.

| Action | Folder admin | Folder editor | Non-member |
|---|:---:|:---:|:---:|
| Read entries | yes | yes | no |
| Create / update / delete entries | yes | yes | no |
| Rename / delete the folder | yes | no | no |
| Add / remove folder members | yes | no | no |

Workspace owners implicitly see and can manage **shared** folders (those with more than one member) for oversight. They cannot see or mutate solo folders — including other users' personal folders — that they're not a member of.

## Personal folders

Each user gets one personal folder on account creation: `entries-{userId}` (display name **My Entries**). The `personal: true` flag is an origin marker, not a sharing lock — owners can share personal folders by granting `folder_access`, and the flag stays true after sharing.

When a user is deleted:

- Their personal folder is renamed to `archive-{slug}-{YYYY-MM-DD}`, the `personal` flag is cleared, and admin transfers to the actor running the delete.
- Any other folder where the deleted user was the **sole** admin transfers to the actor as well, preventing orphaned folders.
- Folders with multiple admins are left alone.

## Per-user API tokens

Tokens minted under **Settings → Connectors → Studiograph MCP** are scoped to the user that minted them. When an MCP client or CLI presents an `sg_` token:

- `req.user` is set to the owning user
- Folder access is enforced per request — the token sees only what its owner sees
- Unauthorized folders return "Folder not found" (never "Forbidden") to avoid leaking existence
- `last_used_at` updates on every successful request

Manage tokens via the API:

```http
POST   /api/auth/tokens         # { name } → { id, name, token } (raw token shown once)
GET    /api/auth/tokens         # list caller's tokens (no raw values)
DELETE /api/auth/tokens/:id     # revoke
```

## Auth seed and portability

The `.studiograph/auth-seed.json` file is the portable form of authentication state:

- All users (with bcrypt password hashes)
- JWT secret (preserved across restores so existing sessions stay valid)
- Workspace API key
- `folder_access` grants by email

The seed is committed to the workspace config repo and auto-exported after every user or access change. On first boot with an empty `auth.db`, the seed is replayed verbatim — same hashes, same secret. This is how Railway deployments stay in sync with local state.

## Embedded Git HTTP

Studiograph runs its own Git HTTP server at `/git/:repo`. It accepts HTTP Basic Auth against `auth-seed.json` credentials, enforces per-folder access on push and fetch, and rate-limits failed logins on the same counter as the web UI. This is what powers `studiograph join` against a self-hosted server without requiring GitHub access.

Before accepting a push, the server commits any pending working-tree state under the `studiograph-recovery` user. This prevents `receive.denyCurrentBranch=updateInstead` from clobbering uncommitted server-side changes.

## Permissions API

Folder-admin endpoints for managing access:

```http
GET  /api/permissions/folders    # all folders with their granted users
POST /api/permissions/grant      # { userId, folder } → grant access
POST /api/permissions/revoke     # { userId, folder } → revoke access
```

These mirror the **Workspace → Manage Folders** settings UI.

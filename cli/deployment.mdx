## Overview

A Studiograph workspace can run in three configurations.

| Mode | Git remote | Best for |
|---|---|---|
| Self-hosted (embedded git) | The Studiograph server itself | Local-first teams; no GitHub dependency |
| Railway + GitHub | GitHub, with webhook-driven pulls | Hosted deployments with team-wide GitHub access |
| Docker | Either | Single-container self-hosting |

All three serve the same Graph API, MCP HTTP endpoint, web UI, and embedded Git HTTP server.

---

## Self-hosted (embedded Git)

Folder repos live directly on the server's disk. The embedded Git HTTP server **is** the git remote — `studiograph join <url>` clones repos via HTTP Basic Auth, and `studiograph push` pushes back the same way. Changes are live immediately on push. No GitHub dependency.

### Setup

```bash
studiograph init "Acme Studios"
cd acme-studios
studiograph serve --port 8000
```

Open the public URL, complete the first-owner setup, then add team members in **Settings → Manage Team**.

### Joining

Each teammate runs:

```bash
studiograph join https://acme.example.com /path/to/local/checkout
```

They'll be prompted for email and password, and every folder they have access to is cloned to their local disk.

### Pre-receive guard

Before accepting a push, the server commits any pending working-tree state under the `studiograph-recovery` user. This prevents `receive.denyCurrentBranch=updateInstead` from clobbering uncommitted server-side changes. The recovery commit is logged in `.studiograph/commit-audit.jsonl`.

## Railway + GitHub

Folder repos live on GitHub, cloned to a persistent Railway volume. A GitHub webhook at `POST /webhooks/github` triggers `git pull` on the relevant folder when push events arrive.

### Deploy

```bash
studiograph deploy railway --name "my-project"
```

The wizard prompts for Railway credentials, sets required environment variables, and pushes the workspace. Credentials are saved to `~/.studiograph/user.json`.

### Required environment variables

| Variable | Description |
|---|---|
| `STUDIOGRAPH_CONFIG_REPO` | GitHub URL to your `.studiograph` config repo |
| `GITHUB_TOKEN` | Fine-grained PAT with repo Contents read access |
| `WEBHOOK_SECRET` | HMAC-SHA256 secret for `/webhooks/github` (optional but recommended) |
| `API_KEYS` | Optional additional Bearer tokens, semicolon-separated |
| `PORT` | Set automatically by Railway |
| `ANTHROPIC_API_KEY` | Required to enable agent chat |

The primary Bearer token is the **workspace API key** (auto-generated by `AuthService` and synced via `auth-seed.json`). `API_KEYS` is only needed for additional tokens — CI pipelines, legacy integrations, etc.

### Bootstrap behavior

On first boot with `STUDIOGRAPH_CONFIG_REPO` set, the server clones the config repo and every content folder. On subsequent boots, it pulls latest changes for all folders. New folders added between deploys are cloned automatically.

### Redeploying

```bash
studiograph redeploy
```

`redeploy` updates the start command to the exact npm version (e.g. `npx --yes studiograph@1.3.3-next.11 serve`) — this avoids stale npm tag caching — and sets a `DEPLOY_TS` env var to force a fresh build cycle.

## Docker

Single-container deployment with a persistent `/workspace` volume.

```bash
docker compose up -d
```

The repo ships a `Dockerfile`, `docker-compose.yml`, and `docker-entrypoint.sh`. The entrypoint:

1. Sets git config (user.name, user.email, safe.directory)
2. Auto-initializes the workspace if `/workspace` is empty
3. Creates an initial admin user from env vars (idempotent)
4. Launches `studiograph serve`

### Environment variables

| Variable | Description |
|---|---|
| `PORT` | Server port (default 8000) |
| `STUDIOGRAPH_TEAM_NAME` | Workspace name for auto-init |
| `ADMIN_EMAIL` | Initial admin email |
| `ADMIN_PASSWORD` | Initial admin password |
| `ADMIN_NAME` | Initial admin display name |
| `API_KEYS` | Optional Bearer tokens |
| `ANTHROPIC_API_KEY` | Enables AI chat |

## Sync between deployments

You can sync a local workspace with a remote server (e.g. promote staging → prod, or snapshot a Railway deployment to your laptop) using `pull --remote` and `push --remote`.

```bash
# Pull config + folder data from a remote
studiograph pull --remote https://schemaos.com --data

# Push local workspace (config + non-personal folders) to a remote
studiograph push --remote https://schemaos.com --data --api-key <key>
```

- Config (auth seed, `workspace.json`, `ABOUT.md`, sources, connectors) is transported via `GET/POST /api/config/bundle`.
- Folder data (with `--data`) flows through the embedded Git HTTP server, so commit history is preserved and conflicts are detected natively.
- Personal folders are skipped — they stay local-only.

Credentials resolve in this order: `--api-key` flag, `STUDIOGRAPH_API_KEY` env, `--email`/`--password` flags, local `auth-seed.json`, then interactive prompts. Agents and CI should use the non-interactive paths.
